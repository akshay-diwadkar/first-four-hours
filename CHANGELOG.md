# Changelog

All notable changes to First Four Hours are recorded in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). [Release Metadata](REPO_VERSIONING.md#release-metadata) says when to add an entry and how a release is prepared.

## [Unreleased]

First Four Hours starts its version history at 1.0.0. Earlier release history stays in the `akshay-diwadkar/skills` repository.

### Added

- Claude Code plugin installation. On Claude Code 2.1.275 or later, install all 15 skills as the `first-four-hours` plugin with `/plugin install first-four-hours --marketplace akshay-diwadkar/first-four-hours`. Plugin skills start as `/first-four-hours:<skill>`, for example `/first-four-hours:diagnose`.
- Charter 1.0.0: a user-invoked Workbench skill, started with `/charter`, that turns a rough ambition for a whole project into one agreed, resumable `.first-four-hours/charters/<slug>/charter.md`. On request it publishes the charter as one GitHub umbrella issue after you confirm the exact text, and never creates tickets.

### Changed

- The Claude Code marketplace and its single plugin are named `first-four-hours`, giving install id `first-four-hours@first-four-hours`. Users of the retired marketplace or the three preview plugins should follow [Replace an earlier plugin installation](docs/getting-started/installation.md#replace-an-earlier-plugin-installation) to remove the old entries before installing the single plugin.
- The repository, every skill, and every contract version the repository owns are now 1.0.0. A skill's version is also the version of every artifact, handoff, receipt, bundle, and state format it owns.
- A consumer accepts another minor or patch version of the same major and refuses any other version.
- Blueprint 1.0.0: before attacking a draft, the fresh challenger walks it in step order and reports any Proof run or Run that needs something not yet created at its phase (a Before implementation Run comes before every instruction), or that works only outside the way Construct launches it: as its own arguments with no shell, from the repository root, in Construct's inherited environment. Planners probe load-bearing commands the same way.
- Blueprint 1.0.0: planners and challengers load a smaller core planning contract on every run. Tracing command dispatch, authoring new step proof, and invoking Ideate are read only when that branch applies. Each Completion Condition is now the one statement of its outcome: a concrete example that names the Run, Proof run, or Exact-text step that shows it, or its owner for an `Owner gate:`. The Goal keeps only its summary. Plans sealed earlier stay valid.
- Blueprint 1.0.0: the fresh challenger now writes the review that a literally built plan would fail, seeded from the repository's planning traps and any review findings in the request. The challenger first checks the plan's tier itself. A plan is elevated if it creates, changes, or deletes code that runs or the configuration it reads, edits something under a budgeted or deadline gate, propagates across skills or packages, has irreversible or outward-facing effects, or changes the seal runtime. An elevated plan's challenger also works through the full attack dimensions, on a model at least as capable as the planner. Every other plan gets the shorter pre-mortem brief and the cheapest capable challenger. Every plan is still challenged.
- Blueprint 1.0.0: the planner first lists the facts its decisions depend on and sends independent questions that are worth delegating to cheap read-only workers together, one question each. A question that needs another's answer waits for it, and only tiny questions stay local, or all of them when no worker can launch. A sealed plan for a similar task may seed a new plan's structure, but every premise and decision taken from it is re-checked against current source and never cited as evidence.
- Blueprint 1.0.0: for each rule the change must never break, the planner decides every producible input, state, configuration, or environment that could still break it, and an elevated challenger lists them again from source, asking of each whether a weak implementation could look compliant while the rule stays breakable. Each guard a rule relies on needs proof that fails when that guard is removed, unless another guard already stops every input that could reach it, and any test double a plan's proof relies on must answer as the real thing it replaces does. A known gap in a requested outcome or rule, whatever input, state, configuration, or environment produces it, is closed or returned to you; the plan seals with it only when your request records that you accepted it. Blueprint's references budget rises from 11750 to 12246 tokens as an owner-approved exception.
- Assess 1.0.0: a gap you accepted, as recorded in the plan's frozen request or other authoritative requirements, is not a finding while the change stays within it; a gap the plan accepted without that record can still be one.
- Construct 1.0.0: the final report lists each after-implementation verification Run with its `Expect:` and whether the output met it, so every check's verdict can be read without rerunning it.
- Atlas 1.0.0: Satellite pages mark where to start reading, cue each other link by the task that needs it, and say when a kind of task has read enough. Navigating agents read the start target first and follow only matching links and cross-links. When a file moves or changes meaning, the agent searches `.map/` for its path to update every pointer citing it. An agent whose work edits files also fixes a cue that misled it, unless its skill limits Atlas upkeep as Construct does.
- Architect, Assess, Atlas, Construct, Ideate, PR, Reason, Scribe, and Ticket 1.0.0 name `charter` among the skills whose suggested next step you run yourself, and Router 1.0.0 knows Charter's handoff to Ticket.
- Architect, Assess, Atlas, Charter, Construct, Ideate, PR, Reason, Scribe, and Ticket 1.0.0 no longer list `pr` among the skills whose suggested next step you run yourself.
- PR 1.0.0: when the branch already has an open pull request, PR replaces that pull request's description with a newly checked one after you confirm the exact text. It keeps what still holds from the current description and changes the title only when you confirm a new one. It looks the pull request up only in the repository the branch was pushed to, and refuses a closed or merged pull request, one opened from another repository, one whose head is not the commit you pushed, and one whose base differs from the base the description was checked against. PR's mode is now `both`: the agent may start it when your request matches, and you can still start it with `/pr`. Opening or updating a pull request still needs your explicit yes.
- Examiner 1.0.0: an on-screen practice paper behaves like a timed examination. A countdown you cannot pause or extend except by a declared access arrangement (extra time, supervised rest breaks), a question list with answered, not answered, and flagged states, work that survives a refresh or a reopened file, an on-screen warning when the browser cannot keep it, timed breaks between papers, a locked paper with an answer file when the last paper ends, and a fresh attempt on request all come from one offline runtime every paper copies. The paper states the examination's sourced rules, including navigation, permitted materials, negative marking, and access arrangements, and labels the runtime's features as practice features, never examination rules.
- Examiner 1.0.0: in an on-screen practice paper, a question flagged for review is marked in orange in the question list, and on a screen at least 1024 px wide (at default text size) the clock, question list, and question buttons stay in a side menu on the left, in the device's light or dark colours, instead of scrolling with the paper. On every screen the question buttons now come before the question list. The repository validator's size cap for the paper runtime rises from 40,000 to 41,000 bytes.
- Examiner 1.0.0: marking says whether its basis is official and, when it is not, whether it is Examiner's own scheme or key, Examiner's unofficial key for a supplied paper, or a correction set's corrected file. It applies each rule only as that basis or the examination's sourced rules state it: assessment-objective weighting, levels of response with their mark bands and placement within a band, consequential marking, an error or contradiction negating a correct response, and negative marking with that examination's own arithmetic. Scoring rules come only from the examination's sourced rules, researched for a supplied paper, and a question flagged for review but not answered scores as unanswered unless the examination scores it otherwise. Each deduction, including a negative mark or a negated point, is explained; the total's aggregation is stated; recorded time is a diagnostic, never part of the score; and a convention neither states is labelled as one and never used to apply those rules. Examiner's own marking schemes state the bands, assessment objectives, and consequential-marking and negation signals the examination's schemes use.
- Tutor 1.0.0: before teaching, practice, or review, Tutor reads a research-grounded guide to choosing how to teach, which says when each method helps and when to stop using it. When an idea is new to you, it opens with what the idea is for and how it works, uses a concrete case from your subject or a comparison of two, uses any analogy only as a bridge with its mapping, where it breaks down, and a counterexample, and says where the idea stops applying. In tutoring and continuing learning, it moves from a worked example through a problem you finish to one you solve alone, and each turn that teaches something new ends with a question you answer from memory with how sure you are, before Tutor gives the answer; a direct explanation still needs no exercises. A check asks for the same kind of thinking on a different case, an idea counts as demonstrated only when more than one task shows it, and each lesson record names the representation that produced the evidence. Help follows what you actually did and shrinks over time, a wrong answer or "I don't know" gets the least help, up to a prompt, a hint, and a worked step, before Tutor gives the answer, feedback addresses the work, review is spaced practice from memory rather than re-reading, and Tutor never claims a learning style, a retention percentage, a brain-based explanation, or a percentage of your understanding.

- Tutor 1.0.0 and Examiner 1.0.0: whenever either saves files for a subject, it creates or refreshes `.learning/<subject>/START_HERE.html`, the page to open first. In plain words it says what each kind of file in the folder is, that any answer key is for after an attempt, which to open first, the next step linked to the study plan when one exists or else to the record that holds it, and what to ask Tutor or Examiner to continue. It is refreshed in place and copies no list of lessons or sets, progress, coverage, or results.
- Diagnose 1.0.0: a probe counts as non-mutating only when it writes nothing into your checkout, its Git metadata, or its ignored or untracked files while it runs. Bisecting history, building, installing, or running tests that write caches happens in a throwaway copy outside your project with its own environment, runs with those writes switched off, or is left for you to run. For a regression from a known-good revision, Diagnose usually reads the history first and bisects only what the history leaves open.

- Reason 1.0.0: a challenge checks its load-bearing claim against an observation instead of rereading the agent's own reasoning. It first states what an economical read, search, run, or test must show, then takes that observation itself when it can do so without changing anything, or names it for the agent to take. It says when its result rests on no observation, and it does not clear a completion claim that any available check could settle until that check is done. It picks that claim by imagining the work has already failed and naming the most plausible cause. It checks the result against the observed output and the request as settled, rather than a restated goal. After a failure, Reason names the assumption the failure disproved, or treats an unknown cause as missing evidence, so a changed approach does not rest on a disproved assumption.

### Removed

- Support for artifacts, receipts, and state written under earlier internal versions. Reseal or regenerate them with the current skills.
