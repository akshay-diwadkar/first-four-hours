# Executable contracts

Read this when the dispatch, runtime mode, installed adapter, phase/state, wrapper semantics, or input spelling of a command, API, integration, or verification path can change its correctness, when interpreter identity or environment setup matters, or when the plan changes tests, fixtures, helpers, or package surfaces, or a Run or Proof run selects a subset of tests.

When interpreter identity matters, use a read-only probe through the relevant subprocess boundary and pin the observed absolute interpreter in environment-sensitive commands when bare-name resolution differs. Put environment creation and dependency installation in implementation preparation; never assume shell activation persists into separately launched commands. A managed base interpreter is not an installable virtual environment. Construct must not silently substitute its own interpreter for an authored command. Checking the real launch path does not require a virtual environment for every task.

When dispatch, runtime mode, installed adapter, phase/state, or wrapper semantics can change correctness, trace the authored invocation through its actual public entrypoint and dispatch to the operation, required inputs and phase/state, and observable result. A matching internal transition or same-purpose helper is not evidence of the public command or the inputs it reads; for a gate over uncommitted changes, trace which paths its entrypoint reads (index, worktree, diff), including planned deletions, renames, and new files. Behavior that depends on how an input is written (link, case, encoding, relative path) always brings the wrapper or runtime between the public command and the changed code into scope: probe the current public command with that kind of input; a library-level probe is only supporting evidence. Distinguish runtime modes; inspect the installed adapter and packaged resources when execution uses them. The affected path is every current consumer, contract, and verification surface touched by the planned diff under current ownership; follow only those contracts, not every internal helper. Declaring a touched surface out of scope requires a source pointer showing no consumer.

## Verification selection

Reconcile verification selection with the complete planned change set: code, tests, helpers, fixtures, package surfaces, and every applicable diff side for renames and deletes. Apply the actual selector's current rule to every planned changed surface, then establish that the authored target set is legal and sufficient for every surface, and that each selected target exists (or is authored by the plan) and is accepted by that selector. Establish acceptance by probing each authored Run's and Proof run's arguments and selector on the current tree, through the tool's dry-run or selection-only mode when it has one; probe a target the plan creates in the same form with an existing target. A consumer exercising a fixture does not establish that the selector accepts the fixture itself, and owner-profile selection does not establish that a selected target imports, reads, or executes a support file. When the selector does not trace that dependency, establish the actual consumer from source or a current safe probe and treat it as agent evidence, not selector proof. If a necessary surface is not selectable or has no valid owner, author the exact repair before seal, including its Location and State, propagation, resulting selection, and a re-check of the complete repaired surface set. Do not invent a target, suppress a path, or leave the repair choice to the executor.
