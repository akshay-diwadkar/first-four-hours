# Incomplete gates

Read this when an authored gate, including a Proof run, could end incomplete on a correct implementation for an environmental reason, or on a `verification.incomplete.*` diagnostic.

A gate a correct implementation can still leave incomplete for an environmental reason (a load-sensitive deadline, an unavailable host service) may declare that outcome on one `Incomplete:` line after its `Expect:`, subject to this rule. The declared signature excludes every outcome of the planned code the output can distinguish, such as recorded failures or a failing worker exit. A deadline cannot tell host load from a planned slowdown or hang, so declare deadline exhaustion only when Current State records headroom the planned change cannot plausibly consume. Headroom comes only from current-tree measurement: the deadline minus a passing current-tree probe's measured elapsed value. Judge whether the planned change can consume it from source, such as the cases and work it adds, never by timing a planned end state. When the planning host cannot produce a passing baseline, a recorded pass elsewhere qualifies only if it ran on the inspected revision or one whose gate-relevant files are unchanged, and the local runs show only the declarable environmental signature: cite that pass and its elapsed value, and record the local outcome. Without such a record, return the conflict to the user before sealing. When the change can consume it, do not declare it, key the planning contract's decided [conditional branch](planning-contract.md#conditional-branches) to a passing run's measured elapsed value, and treat an exhausted deadline, which exits nonzero and cannot trigger that branch, as a real failure. Only the last after-implementation Run can declare, so a plan declares at most one gate: narrow any other environment-sensitive gate, including a Proof run, to a scope a correct implementation completes, recording its headroom, and if that is impossible, return the conflict to the user before sealing. A declared gate's Run still exits `0` on a correct implementation in a healthy environment, and any authored `Timeout:` is well beyond the command's own deadline including startup, because a Construct timeout is unsafe, never incomplete. Construct reports a matching result as incomplete with its output as evidence, never as passed or ready, and never reruns it unchanged. Never make an idle host a precondition.

An `Incomplete:` line follows the last after-implementation Run's `Expect:` at most once; a phase heading ends the earlier Run. The seal rejects one elsewhere in Verification (`verification.incomplete.orphan`), one on a before-implementation Run (`verification.incomplete.before`), a later Run in the same phase (`verification.incomplete.not_last`), a repeat (`verification.incomplete.duplicate`), a placeholder (`verification.incomplete.placeholder`), and one in Implementation (`verification.incomplete.displaced`).
