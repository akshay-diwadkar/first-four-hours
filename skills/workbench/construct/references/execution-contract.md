# Execution Contract

## Trust boundary

Construct consumes one sealed Blueprint and never edits it. Blueprint is the sole semantic authority for requested behavior, scope, seam, files and symbols, control flow, propagation, preservation, compatibility, safety, tests, verification, and completion, except the Atlas upkeep defined under Step proof. Discovery during execution can prove a contradiction, never create an obligation other than that upkeep. The `verify` command is the mechanical establishment boundary: it validates the canonical `.first-four-hours/blueprints/<task>/blueprint.md` path, its canonical `request.md` sibling, the sealed receipts, repository and request binding, planned-source freshness (existing and planned-deleted targets, planned-new absence, declared sources), and the Git worktree before anything runs, then executes exactly the requested phase's authored Run entries. Repository-internal execution and a Blueprint sealed under another contract major fail closed.

## Execute literally

Construct follows the sealed `Implementation` section in order. It must not redesign, choose a different seam, add consumers, tests, cleanup, compatibility, abstractions, robustness, propagation other than Atlas upkeep, API surface, or proof breadth; trim authored work; replace authored verification; run a second YAGNI review; or absorb a newly discovered semantic obligation. Construct writes the code that realizes the authored behavior, interfaces, and pseudocode against their Frozen proof; `apply` writes declared Exact and Frozen text verbatim. Pseudocode fixes decisions, not wording, and grants no license to redesign; a pseudocode decision that conflicts with repository facts is a `plan-contradiction`. Beyond those decisions Construct chooses only local details Blueprint intentionally does not care about, such as syntax glue, formatting, imports, and inconsequential local naming. If two choices can materially alter behavior, ownership, API shape, control flow, propagation, test strategy, compatibility, recovery, or acceptance, Construct must not decide between them: stop with the exact missing Blueprint obligation.

A change that is mechanically necessary to realize an authored instruction stays within non-semantic mechanical fallout: syntax/import/reference repair, or regeneration of authoritative derived output the authored instruction already implies. Changes that alter behavior, policy, ownership, validation scope, typing scope, budgets/exceptions, compatibility, capability meaning, or planned scope are never incidental: if the sealed Blueprint does not authorize one, stop with `plan-contradiction` and the exact missing obligation. An extra material change that serves no instruction is not silently kept: remove it, or stop when source reality proves it genuinely necessary.

Use this boundary consistently:

| Situation | Required behavior |
|---|---|
| Code disagrees with a settled plan instruction | Correct the implementation and rerun invalidated authored verification. |
| Syntax, imports, references, or other mechanical fallout has a determined repair | Repair locally within the declared scope. |
| An authored Run fails because the host sandbox denied a permission the command needs, not because of a code defect | Request that permission and rerun the same authored Run unchanged; never rewrite the Run or substitute an interpreter. |
| A behavior, environment, compatibility, ownership, or verification decision is missing or contradicted | End the Construct invocation and return exact evidence to Blueprint through the caller. |
| Protected work conflicts make continuation unsafe | End this invocation as `protected-work-conflict` (see Stopping); Construct does not restore or continue. |
| Concurrent changes, verification mutation, or uncertain timeout cleanup make continuation unsafe | End this invocation as `safety-contradiction` (see Stopping); never resume from the drifted state. |

Correcting code to match an explicit ordering requirement is implementation repair. Choosing a new environment or weakening a test gate is not automatically incidental merely because it appears operational.

## Verification

`verify` runs authored Run commands verbatim from the repository root: one exact argv command per Run, the authored `Timeout:` honored (default 900 seconds), process-tree cleanup on timeout, full stdout and stderr returned in the result, and a per-step Git index and worktree content mutation guard (the Git index and the full worktree content identity — bytes, size, mode, kind, existence — of all entries, including ignored files and skill workspaces, are bound across every step; Git metadata is excluded and directory links are not followed). Failed Git, traversal, or content observations stop execution as unsafe. Every Run and Proof run inherits the caller's environment with `PYTHONDONTWRITEBYTECODE=1` set, so Python processes that honor it write no bytecode cache; one that strips or replaces its environment, or runs with `-E` or `-I`, still can, and the guard flags it. The returned workspace binds that full identity as `worktree_sha256`; `dirty` lists Git-visible changes only. A failing, timed-out, or repository/index/worktree-mutating Run stops the runner with the step summary and captured output as evidence; nothing is persisted. A timed-out or repository/index/worktree-mutating Run ends this invocation as `safety-contradiction` (see Stopping). `Before implementation` entries run only through phase `before`; when none are authored, the phase returns only the independently necessary establishment checks and no invented test result. After-implementation entries run only through phase `after`, after every authored instruction has been applied.

`Expect:` is agent judgment over the returned output; scripts prove exit, timeout, mutation, and declared exact text only, and never judge whether the code satisfies an instruction. When stdout is JSON or JSON-object lines, the result also carries it parsed as `stdout_json`; a record a check itself marks `"slow": true` appears in `notices` on verify, prove, status, and their partial results as information that never changes pass/fail. Exit 0 does not excuse an unmet Expect. Judge every authored `Expect:` against the returned output; an unsatisfied Expect with no authored branch and no Blueprint-settled correct answer is a Blueprint contradiction, not a local repair target. Do not substitute a larger suite, add neighboring tests, or broaden proof.

A failing Run with a declared `Incomplete:` outcome returns that declaration in `details.incomplete`, no `next_command`, and any repair `reverify` command in `details.reverify_command`. When its output shows the declared outcome and no failure the declaration does not explain, report verification incomplete with that output as evidence: never passed, not a plan contradiction, and never rerun unchanged. The declaration is the authored branch: after the reconciliation pass the run ends as `verification-incomplete`, reporting the applied implementation and that evidence; it is neither completion nor a stop classification, and readiness still needs a complete passing run. "Never rerun unchanged" binds this Construct invocation; whether and when a fresh Construct invocation retries is the caller's decision. Otherwise the failure is real and follows the local-repair boundary below.

The local-repair boundary is:

```text
failed or unsatisfied authored check
  -> if the sealed Blueprint already fixes the correct answer, repair the
     coding/transcription/import/syntax/mechanical defect and reverify from the
     earliest invalidated or previously unrun authored Run line
  -> otherwise stop with exact plan-contradiction evidence
```

The repair-only `reverify` selection executes one authored after-implementation Run and every later authored entry in existing order; its `from_line` must exactly match an authored after-Run line. Earlier successes stand when the agent judges them unaffected; timeout and mutation failures never advertise `reverify` or authorize in-run recovery. Reuse an observed success only while its relevant source, inputs, environment, and prerequisites remain unchanged; uncertainty earns a rerun. The same observed result on unchanged relevant state satisfies an identical obligation once, while distinct affected, full, context, installation, and repository obligations still run. Add no cache, receipt, resume token, dependency inference, or generalized scheduler. Repository-required checks authored in the sealed Blueprint run in Construct. The caller owns any remaining repository-required checks.

## Step proof

An instruction may declare `**Exact:**` implementation text, `**Frozen:**` planner-authored proof (tests or break-the-code checks), and one `**Proof run:**`. A block with one fence is a new file's whole content; a fence, `**With:**`, and a second fence replace the first text with the second in an existing file. Each block is `exact` (whole file equal, or the replacement occurs exactly once at a line boundary with the replaced text gone outside it), `unapplied` (new file absent, or the replaced text occurs once and substituting it would be `exact`), or `diverged`. Comparison is UTF-8 text with CRLF read as LF. The seal simulates a faithful executor instruction by instruction, Frozen then Exact, sharing file state across path aliases, and proves every check below passes on its declared text; undeclared edits to the same files can still contradict.

- **Apply.** `apply` writes one instruction's declared blocks so the executor never hand-copies them: `blocks=frozen` or `blocks=exact` selects one kind, and omitting it applies Frozen then Exact, which a `Red:` instruction with Exact text refuses because its red comes first. It replays the seal's simulation on the current files: earlier instructions' blocks and, for Exact text, this instruction's Frozen blocks must be `exact`, and earlier instructions' planned deletions must be carried out; selected blocks already `exact` stay untouched, and each other one must be `unapplied` and land exactly once at a line boundary. A diverged block, nothing left to apply, or any failed check refuses the whole call with the mismatch and writes nothing, so diverged or already-applied text is never overwritten. It writes only those blocks' Location files: replaced lines take CRLF when the file has any, every other byte stays, and a new file holds its declared LF text. Specified work stays the agent's. A write failure stops as `safety-contradiction`. When an instruction still has `unapplied`, undiverged declared text, the command Construct returns for it is `apply`, with two exceptions: a `Red:` instruction whose Exact text is all unapplied and whose planned deletions are not yet carried out resumes at `prove` red once its Frozen text exists, and a Proof run that cannot launch keeps its `prove` route. On a `Red:` instruction, `apply` covers only Frozen text until red is observed, Exact text has started, or a planned deletion is carried out. Diverged text keeps the `prove` route for repair.
- **Red.** Only a Proof run that declares `Red:` is a new regression. `apply` its Frozen blocks, then `prove` red while its Exact blocks are `unapplied`: it must fail, and the agent confirms the output shows the declared defect: the regression itself ran and failed because of the wrong behavior `Red:` names, however that failure surfaces (exit code, diagnostic, exception, or first failing assertion). A failure from a missing import, broken collection, unavailable tool, or another cause, or a regression left unexecuted because another case failed first, is not that red: stop as `plan-contradiction`. A red that passes while unapplied stops as `plan-contradiction`. One that cannot launch, or whose runner reports it blocked by its environment (such as lock contention or an exhausted deadline) with no failed case, is incomplete: stop without rerunning and report that environmental block, never as the red. Red after Exact text has started or a planned deletion is carried out is refused: report the red observation as an unrecoverable gap. A step with `Red:` and neither an Exact block nor a `deleted` Location cannot detect this, so its red still reports `plan-contradiction`. Existing green checks need no red. Red carries the caller's next green `attempt` unchanged and consumes none; with Exact text still to apply, its `judge` names that green attempt. Red is Construct's observation; authored Runs still pass only on exit 0.
- **Green.** `prove` green checks the instruction's blocks and runs its Proof run. `unapplied` Frozen proof is the next action and uses no attempt; `diverged` Frozen proof stops as `plan-contradiction` (never edit frozen proof), so a mistyped Frozen block is local at red but terminal at green. A Proof run that cannot launch uses no attempt and is reported as unavailable, never as an implementation failure. A failing attempt returns the mismatch diff, full output, the instruction's diff, and the next attempt's command. Attempt 3 failing stops with that evidence. The caller retains each instruction's next unused attempt across invocations; commands validate 1-3 but cannot detect falsely supplied history. Missing or exhausted history stops this run, never resets to 1; a justified fresh run requires current authority and a trustworthy worktree. Successful green returns forward guidance derived from the sealed instruction order, never a resume scan or guessed counter. Before advancing, confirm the current instruction realizes its authored behavior and preservation rules, and judge its `Expect:`. For a non-final instruction, `proof.next_instruction` names the next number and `proof.required_action` gives its Frozen/implementation/red/green sequence using that instruction's caller-held next unused attempt; `next_command` is null because its budget is unknown. The final green returns the authored `verify` after command. A `deleted` Location is mechanical proof by absence: green fails, using its attempt, while the path still exists. An instruction without mechanical proof retains `unprovable` and the same conditional forward guidance; it does not gain a fabricated proof result. `prove` first rechecks every earlier instruction's blocks and planned deletions; unproven earlier text points back to `status`, and becomes `plan-contradiction` only when a later edit changed text already proven in this run.
- **Resume.** `status` derives progress from the sealed plan and current worktree only: it reruns read-only green proof, never replays red or a non-idempotent action, and reports a satisfied regression's red as `unrecoverable`. An instruction is `satisfied` only through `exact` Exact text, a carried-out `deleted` Location, or a passing declared regression; one whose checks pass without that evidence, or that has no mechanical proof, stops as `status.progress_unverifiable` for caller diff judgment, even when its targets match their sealed bytes; a deleted path still holding its sealed bytes keeps its instruction pending. Later instructions stay `not_checked`; no next command skips uncertain work. A Proof run that cannot launch stops as `status.proof_unavailable`: report the gap. Bare `status` identifies pending work without issuing an attempt; paired `instruction` and `attempt` inputs supply the caller's next unused counter for only the first pending or diverged instruction. A different instruction fails as `status.attempt_context_mismatch`; context cannot clear uncertain progress. `diverged` text stops as `status.diverged`, without an automatic next command. Its `details.own_edit_command` exists only with matching supplied context and no diverged Frozen proof: use it only for your own transcription in this run; otherwise the plan is stale. Frozen proof remains immutable. During resume, only all-satisfied status routes to final verification; normal in-session execution uses the forward guidance above. Source-only evidence must still match its sealed bytes before any resumed command runs. Source/target exemptions use normalized authored names, never a newly followed link; non-regular or escaping sources fail closed. Changed targets with no Exact/Frozen text stop automatic resume as `status.progress_unverifiable`, with no next command: the caller reconciles them before using in-session proof commands; a carried-out deletion is not such a change, but a deleted target whose bytes changed is. `verify` phase `before` names drift as `blueprint.invalid` and advertises `status` only when every changed path has declared text or is a carried-out planned deletion. Another writer's edit outside declared text during a resumed run is undetectable without stored state.
- **Final.** `verify` phase `after` reproves every block and planned deletion first: `unapplied` blocks and still-present `deleted` paths report `verification.instruction_unapplied` with a `status` command, including dependent anchors created by skipped earlier instructions. Diagnostic-only replay names those prerequisites but never counts projected text as applied. Real `diverged` blocks remain `plan-contradiction`, retaining mixed omission evidence. Exact proof covers declared text only, not semantic completeness.

Atlas upkeep is mechanical link repair: one sweep from current state after the last instruction, before running any `verify` phase `after` command, including one that a final green or `status` returns. For each file a `deleted` Location removed, find every link in `MAP.md` or under `.map/` whose target, ignoring any `#fragment`, resolves to that file. Before editing anything, give each found link the first outcome that applies:
1. `plan-contradiction`: the link sits on a plan Location or Source page, is not inline, is outside a list item, shares its item with another link, or targets a wiki page; or an instruction names that file's move or rename to a new path that is not a regular file.
2. rewrite: an instruction names that file's move or rename to a new path that is a regular file. The target becomes that path, relative to the page, keeping any fragment.
3. remove: any other link. Its list item is removed. Then judge each page's rewrites and removals together: when the page would have no project-file link after all of them, each removal on it becomes `plan-contradiction`. Then every remaining rewrite or removal on a page in Safety's protected set becomes `protected-work-conflict`. If any link has a stop class, repair none and stop once: as `plan-contradiction` when any link has that class, otherwise as `protected-work-conflict`, naming every stopped link with its class. Otherwise apply every rewrite and removal. Never edit cue text, remap, or add pages. Wherever this contract or `SKILL.md` bars unplanned obligations, scope, files, propagation, or changes, this repair counts as authorized, and it leaves no choice under Execute literally. Report each repair, and list without editing, for planning, the other pointers whose cited file an instruction changed.

## Reconciliation and completion

Before declaring completion, run one bounded reconciliation pass comparing the sealed Implementation against the actual final Git diff. The pass has one checkable outcome: the final diff realizes every instruction, contains no unauthorized material change, and preserves every authored and unrelated-work constraint. Derive the material changed paths from Git (`git status --porcelain` and the diff) and compare them against the authored `**Location:**` targets and Atlas upkeep; an unattributed material path is removed or stops execution. Repair only mechanical execution mistakes already unambiguously settled by Blueprint; return every new semantic necessity to Blueprint with the exact evidence. A supported finding is never absorbed: stop with the evidence instead. One earned fresh read-only reviewer (see Earned Conformance Review) may confirm the reconciliation for non-trivial, materially risky changes; its result is reported to the caller, never persisted.

Completion is a caller-facing report: authored implementation applied in order, authored after-implementation verification passed, and the final diff realizes every instruction without unauthorized material change, with protected unrelated work and HEAD unchanged. Semantic completion remains grounded in the Blueprint's authored observable conditions; Construct does not invent acceptance criteria. A Completion Condition starting `Owner gate:` belongs to the owner it names: report it as pending, and never attempt or claim it. Inspect unexpectedly large changed-line counts for line-ending churn and renormalize only touched files. Commit, push, and other publication effects happen after completion and remain outside Construct.

## Stopping

Stopping ends the invocation, is reported to the caller, and is never persisted. Three classifications, each with a distinct recovery owner:

- `plan-contradiction` — Blueprint is stale, incorrect, or incomplete: relevant source drift after seal, a required symbol or API missing or materially different, a newly discovered consumer that makes the authored solution incorrect, an internally contradictory or impossible authored implementation, a missing authored branch for a discovered outcome, an unplanned semantic requirement the sealed Blueprint does not authorize, or authored verification failing with no authored branch that applies.
- `protected-work-conflict` — continuing would overwrite or destroy protected unrelated dirty work; this invocation stops and the work's owner resolves the conflict before a fresh Construct invocation.
- `safety-contradiction` — an authored safety constraint cannot be satisfied, or the execution baseline moved concurrently (HEAD moved, verification mutated the repository/index/ worktree, or verification timed out with uncertain descendant cleanup); this invocation stops, and the caller establishes a trusted state outside it before any fresh Construct invocation.

Stopping is terminal for that Construct run: after stopping, Construct never amends or reseals the Blueprint, never assumes Blueprint ownership, and never continues execution under another role. It does not automatically end an already-authorized implementation task. Construct never consults Reason or Ideate to fill a planning gap. The composition is one-way — Blueprint seals, Construct executes. A `plan-contradiction` returns evidence to the caller; an amendment is a separate Blueprint invocation over the original request, acceptance conditions, current worktree, and exact contradiction evidence, and execution resumes only in a fresh Construct run against a new sealed plan in a fresh task directory. Except after `verification.mutated_workspace`, a `protected-work-conflict` or `safety-contradiction` never amends the plan: after its named owner re-establishes a safe state, any further execution is a fresh Construct invocation whose intake must validate the existing sealed plan. After that mutation stop, once the caller establishes a trusted state, it takes the stopped command, `changed_paths`, and `index_changed` to a Blueprint amendment as for a `plan-contradiction`, never rerunning that sealed plan unchanged.

The old request and sealed Blueprint remain immutable. The revision must account for the entire remaining obligation, including previously applied work; created files are now existing targets whose current bytes must be bound when further edits are planned, and unrelated dirty work remains protected. Planning-only requests still end after planning. Implementation requests continue through the authorized stages. A repeated unresolved contradiction must not trigger an unchanged retry or an unbounded revision loop.

A stop names the authored instruction that cannot continue, the exact conflicting path/symbol/condition, the observed repository or verification fact, why it contradicts the sealed Blueprint, and whether any authored branch applies.
