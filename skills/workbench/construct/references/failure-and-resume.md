# Failure, resume, and stopping

## Failing Runs

A failing Run with a declared `Incomplete:` outcome returns that declaration in `details.incomplete`, no `next_command`, and any repair `reverify` command in `details.reverify_command`. When its output shows the declared outcome and no failure the declaration does not explain, report verification incomplete with that output as evidence: never passed, not a plan contradiction, and never rerun unchanged. The declaration is the authored branch: after the reconciliation pass the run ends as `verification-incomplete`, reporting the applied implementation and that evidence; it is neither completion nor a stop classification, and readiness still needs a complete passing run. "Never rerun unchanged" binds this Construct invocation; whether and when a fresh Construct invocation retries is the caller's decision. Otherwise the failure is real and follows the local-repair boundary below.

The local-repair boundary is:

```text
failed or unsatisfied authored check
  -> if the sealed Blueprint already fixes the correct answer, repair the
     coding/transcription/import/syntax/mechanical defect and reverify from the
     earliest invalidated or previously unrun authored Run line
  -> otherwise stop with exact plan-contradiction evidence
```

The repair-only `reverify` selection executes one authored after-implementation Run and every later authored entry in existing order; its `from_line` must exactly match an authored after-Run line. Earlier successes stand when the agent judges them unaffected; timeout and mutation failures never advertise `reverify` or authorize in-run recovery. Reuse an observed success only while its relevant source, inputs, environment, and prerequisites remain unchanged; uncertainty earns a rerun. The same observed result on unchanged relevant state satisfies an identical obligation once, while distinct affected, full, context, installation, and repository obligations still run. Add no cache, receipt, resume token, dependency inference, or generalized scheduler. Repository-required checks authored in the sealed Blueprint run in Construct. The caller owns any remaining repository-required checks.

## Mutation guard

Guarded content is every Git-visible entry (tracked, or untracked and not ignored, with a nested repository or submodule listed the same way by its own Git) and every plan-bound path (each Location and Source, ignored or not, and the task's `request.md` and `blueprint.md`); its content identity — bytes, size, mode, kind, existence — the Git index, and HEAD are bound across every step, Git metadata is excluded, and directory links are not followed. Other Git-ignored content, such as tool caches, build output, environment folders, and other skill workspaces, is never observed, so a write there never stops a step. Failed Git, traversal, or content observations of guarded content stop execution as unsafe. Every Run and Proof run inherits the caller's environment with `PYTHONDONTWRITEBYTECODE=1` set, so Python processes that honor it write no bytecode cache; one that strips or replaces its environment, or runs with `-E` or `-I`, still can, and the guard flags it when that cache is guarded content. The returned workspace binds that guarded identity as `worktree_sha256`; `dirty` lists Git-visible changes only.

## Resume

`status` derives progress from the sealed plan and current worktree only: it reruns read-only green proof, never replays red or a non-idempotent action, and reports a satisfied regression's red as `unrecoverable`. An instruction is `satisfied` only through `exact` Exact text, a carried-out `deleted` Location, or a passing declared regression; one whose checks pass without that evidence, or that has no mechanical proof, stops as `status.progress_unverifiable` for caller diff judgment, even when its targets match their sealed bytes; a deleted path still holding its sealed bytes keeps its instruction pending. Later instructions stay `not_checked`; no next command skips uncertain work. A Proof run that cannot launch stops as `status.proof_unavailable`: report the gap. Bare `status` identifies pending work without issuing an attempt; paired `instruction` and `attempt` inputs supply the caller's next unused counter for only the first pending or diverged instruction. A different instruction fails as `status.attempt_context_mismatch`; context cannot clear uncertain progress. `diverged` text stops as `status.diverged`, without an automatic next command. Its `details.own_edit_command` exists only with matching supplied context and no diverged Frozen proof: use it only for your own transcription in this run; otherwise the plan is stale. Frozen proof remains immutable. During resume, only all-satisfied status routes to final verification; normal in-session execution uses the forward guidance above. Source-only evidence must still match its sealed bytes before any resumed command runs. Source/target exemptions use normalized authored names, never a newly followed link; non-regular or escaping sources fail closed. Changed targets with no Exact/Frozen text stop automatic resume as `status.progress_unverifiable`, with no next command: the caller reconciles them before using in-session proof commands; a carried-out deletion is not such a change, but a deleted target whose bytes changed is. `verify` phase `before` names drift as `blueprint.invalid` and advertises `status` only when every changed path has declared text or is a carried-out planned deletion. Another writer's edit outside declared text during a resumed run is undetectable without stored state.

## Stopping

Stopping ends the invocation and is never persisted. Each classification has its own recovery owner:

- `plan-contradiction` — Blueprint is stale, incorrect, or incomplete: relevant source drift after seal, a required symbol or API missing or materially different, a newly discovered consumer that makes the authored solution incorrect, an internally contradictory or impossible authored implementation, a missing authored branch for a discovered outcome, an unplanned semantic requirement the sealed Blueprint does not authorize, or authored verification failing with no authored branch that applies.
- `protected-work-conflict` — continuing would overwrite or destroy protected unrelated dirty work; this invocation stops and the work's owner resolves the conflict before a fresh Construct invocation.
- `safety-contradiction` — an authored safety constraint cannot be satisfied, or the execution baseline moved concurrently (HEAD moved, verification mutated the repository/index/ worktree, or verification timed out with uncertain descendant cleanup); this invocation stops, and the caller establishes a trusted state outside it before any fresh Construct invocation.

Stopping is terminal for that Construct run: after stopping, Construct never amends or reseals the Blueprint, never assumes Blueprint ownership, and never continues execution under another role. It does not automatically end an already-authorized implementation task. Construct never consults Reason or Ideate to fill a planning gap. The composition is one-way — Blueprint seals, Construct executes. A `plan-contradiction` returns evidence to the caller; an amendment is a separate Blueprint invocation over the original request, acceptance conditions, current worktree, and exact contradiction evidence, and execution resumes only in a fresh Construct run against a new sealed plan in a fresh task directory. Except after `verification.mutated_workspace`, a `protected-work-conflict` or `safety-contradiction` never amends the plan: after its named owner re-establishes a safe state, any further execution is a fresh Construct invocation whose intake must validate the existing sealed plan. After that mutation stop, once the caller establishes a trusted state, it takes the stopped command, `changed_paths`, `index_changed`, and `head_changed` to a Blueprint amendment as for a `plan-contradiction`, never rerunning that sealed plan unchanged.

The old request and sealed Blueprint remain immutable. The revision must account for the entire remaining obligation, including previously applied work; created files are now existing targets whose current bytes must be bound when further edits are planned, and unrelated dirty work remains protected. A repeated unresolved contradiction must not trigger an unchanged retry or an unbounded revision loop.

A stop names the authored instruction that cannot continue, the exact conflicting path/symbol/condition, the observed repository or verification fact, why it contradicts the sealed Blueprint, and whether any authored branch applies.
